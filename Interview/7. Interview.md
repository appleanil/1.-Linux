# Linux Interview Scenarios: 10 Real-Time Questions and Answers

## 1. You accidentally deleted an important file. How would you recover it in Linux?

### Scenario
An application log or configuration file was accidentally deleted from an ext4 filesystem, and no recent backup exists.

### Key Facts
- On ext4/XFS, deleting a file removes its directory entry and reduces its inode link count.
- Data blocks may remain on disk until overwritten, but recovery is not guaranteed.
- Recovery chances decrease as the filesystem continues writing data.

### Step 1: Stop Writes to the Filesystem

Identify the filesystem containing the deleted file:

```bash
findmnt /data
df -h /data
```

If possible, stop applications writing to the filesystem and unmount it:

```bash
sudo sync
sudo umount /data
```

If unmounting is not possible, consider taking the filesystem offline or using an appropriate read-only recovery workflow. Do not blindly remount the root filesystem read-only on a production server.

### Step 2: Create a Disk Image

Use a separate disk or recovery destination with enough free space.

```bash
sudo dd if=/dev/sdX of=/mnt/recovery/disk.img bs=4M conv=noerror,sync status=progress
```

Replace `/dev/sdX` with the correct source device. Ideally, use a write blocker or a recovery tool designed to image failing disks.

### Step 3: Try Filesystem Recovery Tools

**For ext3/ext4:**

```bash
sudo extundelete /dev/sdX --restore-file path/to/important.conf
sudo extundelete /dev/sdX --restore-directory path/to/dir
```

Run these against the correct unmounted filesystem or a suitable image, and follow the tool's requirements. XFS is not supported by `extundelete`.

**For file carving:**

```bash
sudo photorec
```

PhotoRec may recover file contents, but original filenames and directory structures might be lost.

### Step 4: Recover a File Still Open by a Process

If a process still has the deleted file open, its contents may be recoverable through `/proc`.

```bash
sudo lsof | grep '(deleted)'
```

Suppose the process ID is `1234` and the file descriptor is `4`:

```bash
sudo cat /proc/1234/fd/4 > /tmp/important.log.recovered
```

### Preventive Measures
- Configure regular backups.
- Use LVM, ZFS, or Btrfs snapshots where appropriate.
- Ship application logs to a remote logging system.
- Configure log rotation.

### Interview Answer
First, I would stop writes to the affected filesystem to reduce the chance of overwriting the deleted data. Then I would create a disk image and attempt recovery using filesystem-specific tools or PhotoRec. If a process still had the deleted file open, I would check `/proc/<PID>/fd/`. Finally, I would implement backups and snapshots to prevent similar incidents.

## 2. A user cannot access a file even though they have read permissions. What could be the issue?

### Common Root Causes

1. Missing execute (`x`) permission on a parent directory.
2. Access Control Lists (ACLs) restricting access.
3. SELinux or AppArmor security policies.
4. NFS UID/GID mapping problems or `root_squash`.
5. Filesystem or mount restrictions.

### Step 1: Check Directory Permissions

```bash
namei -l /path/to/file
```

Every parent directory requires execute (`x`) permission for path traversal.

### Step 2: Check ACLs

```bash
getfacl /path/to/file
getfacl /path/to/parent
```

### Step 3: Check SELinux and AppArmor

```bash
ls -Z /path/to/file
sudo ausearch -m AVC -ts recent
sudo aa-status
```

### Step 4: Check NFS and User Identity

```bash
mount | grep nfs
id username
```

### Example Fixes

Grant directory traversal permission when appropriate:

```bash
sudo chmod o+x /path/to
```

Grant a specific user read access through an ACL:

```bash
sudo setfacl -m u:student:r /path/to/file
```

Restore expected SELinux contexts when they are incorrect:

```bash
sudo restorecon -Rv /path/to
```

### Interview Answer
I would verify permissions on the file and every parent directory using `namei -l`. Then I would check ACLs, SELinux/AppArmor logs, and NFS identity mapping. Standard read permissions alone do not guarantee access if another security layer blocks it.

## 3. You need to find and delete all log files older than 30 days.

### Step 1: Perform a Dry Run

```bash
sudo find /var/log -type f -name '*.log' -mtime +30 -print
```

Review the output before deleting anything.

### Step 2: Delete Matching Files

```bash
sudo find /var/log -type f -name '*.log' -mtime +30 -delete
```

`-mtime +30` selects files whose modification time falls into the range matched by GNU `find`'s day-based calculation. It does not mean an exact 30 × 24-hour cutoff.

### Include Compressed Logs

```bash
sudo find /var/log -type f \
  \( -name '*.log' -o -name '*.gz' \) \
  -mtime +30 -print
```

After reviewing the output, replace `-print` with `-delete` to remove the matching files.

### Clean Up systemd Journal Logs

Preview journal disk usage:

```bash
sudo journalctl --disk-usage
```

Retain approximately the last 30 days of journal entries:

```bash
sudo journalctl --vacuum-time=30d
```

### Interview Answer
I would first run `find` with `-print` to verify which files match the criteria. After confirming the list, I would use `-delete`. For systemd journal logs, I would use `journalctl --vacuum-time=30d`.

## 4. A directory has thousands of files, and `rm -rf` is taking too long. How can you speed it up?

### Method 1: Use `find -delete`

```bash
find /bigdir -type f -delete
find /bigdir -depth -type d -empty -delete
```

The first command deletes files. The second removes empty directories, processing deeper directories first.

### Method 2: Use Parallel Deletion

```bash
find /bigdir -type f -print0 |
  xargs -0 -r -P 8 rm -f --
```

This starts up to eight parallel `rm` processes. It may help when the storage can handle concurrent operations, but it can also increase I/O contention.

### Method 3: Use rsync

For an existing directory that needs to be emptied, an empty source can be used carefully:

```bash
mkdir -p /tmp/empty-dir
rsync -a --delete /tmp/empty-dir/ /bigdir/
```

**Warning:** `rsync --delete` removes destination entries that are absent from the source. Verify both paths carefully before running it.

### Method 4: Delete a Btrfs Subvolume

If the directory is a Btrfs subvolume, deleting the subvolume may be more efficient than deleting individual files:

```bash
sudo btrfs subvolume delete /bigdir
```

### Interview Answer
I would first identify whether the delay is caused by filesystem metadata operations or storage I/O. I could use `find -delete`, controlled parallel deletion, or a filesystem-specific feature such as Btrfs subvolume deletion. I would verify the target path before using any destructive command.

## 5. How do you find the top 10 largest files on a Linux system?

### Search the Current Filesystem

```bash
sudo find / -xdev -type f -printf '%s %p\n' 2>/dev/null |
  sort -nr |
  head -n 10
```

- `-xdev`: Avoid crossing into other mounted filesystems.
- `-type f`: Search regular files.
- `-printf '%s %p\n'`: Print file size in bytes and the path.
- `sort -nr`: Sort numerically in descending order.
- `head -n 10`: Show the first ten results.

### Search a Specific Directory

```bash
sudo find /var -type f -printf '%s %p\n' 2>/dev/null |
  sort -nr |
  head -n 10
```

### Interview Answer
I would use `find` to list file sizes and paths, sort the results numerically in descending order, and display the first ten entries. I would use `-xdev` when I want to restrict the search to the filesystem containing `/`.

## 6. A script is failing with "Permission denied", even as root. What could be the reason?

### Common Causes

1. Missing execute permission.
2. Incorrect shebang or missing interpreter.
3. Windows CRLF line endings.
4. A filesystem mounted with `noexec`.
5. SELinux or another security policy.
6. Script or parent directory restrictions.

### Step 1: Check File Permissions

```bash
ls -l script.sh
chmod +x script.sh
```

Only change permissions when appropriate.

### Step 2: Check the Shebang and Line Endings

```bash
head -n 1 script.sh
file script.sh
```

If the file uses Windows line endings:

```bash
dos2unix script.sh
```

### Step 3: Check the Interpreter

```bash
command -v bash
command -v python3
```

For a Bash script, test whether it runs through the interpreter:

```bash
bash script.sh
```

### Step 4: Check Mount Options

```bash
findmnt -T /path/to/script.sh -o TARGET,OPTIONS
```

If the filesystem is mounted with `noexec`, direct execution may be blocked. Follow the system's security requirements rather than casually disabling this protection.

### Step 5: Check SELinux

```bash
ls -Z /path/to/script.sh
sudo ausearch -m AVC -ts recent
```

Restore the expected context if necessary:

```bash
sudo restorecon -v /path/to/script.sh
```

### Interview Answer
I would check the file permissions, shebang, line endings, interpreter availability, and mount options. If these are correct, I would inspect SELinux or other security-policy logs. Root access does not bypass every kernel or security restriction.

## 7. You need to rename multiple files that have spaces in their names.

### Method 1: Use a Safe Bash Loop

Replace spaces with underscores in filenames in the current directory:

```bash
find . -maxdepth 1 -type f -name '* *' -print0 |
while IFS= read -r -d '' file; do
  new_name="${file// /_}"
  mv -i -- "$file" "$new_name"
done
```

- `-print0`: Separates filenames with null characters.
- `read -r`: Prevents backslash interpretation.
- Quoting protects filenames containing spaces.
- `mv -i`: Prompts before overwriting an existing destination.

### Method 2: Use Perl `rename`

On systems that provide the Perl version of `rename`:

```bash
rename 's/ /_/g' -- *\ *
```

Check the installed implementation and its syntax before using it, because different Linux distributions provide different `rename` commands.

### Interview Answer
I would use a null-delimited `find` pipeline and quote every filename to safely handle spaces and special characters. I would use `mv -i` to avoid accidental overwrites.

## 8. How do you compare two directories and find differences in files?

### Method 1: Compare Directory Contents

```bash
diff -rq dirA dirB
```

- `-r`: Recursively compares subdirectories.
- `-q`: Reports whether files differ without displaying complete content differences.

### Method 2: Display Content Differences

```bash
diff -ruN dirA dirB | less
```

- `-u`: Displays unified differences.
- `-N`: Treats missing files as empty files in the comparison.

### Method 3: Compare File Checksums

```bash
(
  cd dirA &&
  find . -type f -print0 |
  sort -z |
  xargs -0 -r md5sum
) > /tmp/a.md5

(
  cd dirB &&
  find . -type f -print0 |
  sort -z |
  xargs -0 -r md5sum
) > /tmp/b.md5

diff -u /tmp/a.md5 /tmp/b.md5
```

This checksum approach helps compare file contents and relative paths. For security-sensitive integrity checks, prefer SHA-256:

```bash
sha256sum filename
```

### Interview Answer
I would use `diff -rq` for a quick recursive comparison and `diff -ruN` to inspect content changes. If I needed to verify file integrity, I would compare checksums such as SHA-256.

## 9. A user cannot create files in a directory, but `ls -l` shows they have write permission. What could be the problem?

### Common Root Causes

1. Missing execute (`x`) permission on the directory.
2. Filesystem is full.
3. Inodes are exhausted.
4. ACL restrictions.
5. Immutable attributes.
6. User or group quota exceeded.
7. Read-only filesystem or NFS restrictions.

### Step 1: Check Directory Permissions

```bash
ls -ld /shared/dir
namei -l /shared/dir
```

Creating files requires both write (`w`) and execute (`x`) permissions on the directory.

### Step 2: Check Disk Space and Inodes

```bash
df -h /shared/dir
df -i /shared/dir
```

### Step 3: Check ACLs

```bash
getfacl /shared/dir
```

### Step 4: Check Immutable Attributes

```bash
lsattr -d /shared/dir
```

If the immutable attribute is present and removal is authorized:

```bash
sudo chattr -i /shared/dir
```

### Step 5: Check Quotas and Mount Options

```bash
quota -u username
findmnt -T /shared/dir -o TARGET,OPTIONS
```

### Example Fix

If the directory owner should have full access:

```bash
sudo chmod u+rwx /shared/dir
```

Apply permission changes only after confirming the intended owner and access policy.

### Interview Answer
I would verify that the user has both write and execute permissions on the directory, then check disk space, inode availability, ACLs, immutable attributes, quotas, and mount options. Write permission alone is insufficient to create a file if another requirement is not satisfied.

## 10. A symbolic link you created is broken. How do you troubleshoot and fix it?

### Step 1: Inspect the Link

```bash
ls -l linkname
readlink linkname
readlink -f linkname
file linkname
```

A symbolic link may be broken because:

- The target file or directory was deleted.
- A relative target became invalid after moving the link.
- The link points to the wrong location.
- Permissions or security policies prevent access to the target.

Note that `readlink -f` may return no result for a nonexistent target.

### Step 2: Recreate the Link

For a system path, use an absolute target when appropriate:

```bash
ln -sfn /correct/absolute/path target_link
```

For a relocatable application directory, a relative link may be preferable:

```bash
ln -s ../shared/config.yaml app/config.yaml
```

**Warning:** `ln -sfn` can replace an existing link. Verify the destination first, especially if it might be a real directory.

### Step 3: Check for Broken Links

```bash
find . -type l ! -exec test -e {} \; -print
```

This lists symbolic links whose targets do not exist.

### Interview Answer
I would inspect the link with `ls -l` and `readlink`, verify that the target exists, and determine whether the problem is caused by an incorrect path or a moved target. I would recreate the link with the correct absolute or relative path and verify it afterward.

# Appendix B: Operational Guardrails

1. Always preview destructive operations before executing them.
2. Verify the target path before using `rm`, `find -delete`, `rsync --delete`, or `chattr`.
3. Avoid unnecessary writes to a filesystem when recovering deleted data.
4. Check both disk capacity and inode availability when file creation fails.
5. Use least-privilege permissions instead of broad permissions such as `chmod 777`.
6. Back up important configuration files and application data regularly.
7. Use monitoring and centralized logging to improve troubleshooting.

---

# Appendix C: Linux Interview Answer Framework

Use this structure to explain real-world troubleshooting scenarios during interviews.

1. **Situation:** Explain the problem and its impact.
2. **Investigation:** Describe the commands and checks performed.
3. **Root Cause:** Identify the specific permission, filesystem, configuration, or security issue.
4. **Resolution:** Explain the corrective action and how you verified it.
5. **Prevention:** Describe the backup, monitoring, automation, or security improvement that prevents recurrence.

**Final Interview Tip:** Explain not only which command you would run, but also why you would run it, what result you expect, and how you would verify the fix.
